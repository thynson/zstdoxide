# Dictionary conformance fixtures and test plan

Reference: facebook/zstd v1.5.7, revision
`f8745da6ff1ad1e7bab384bd1f9d742439278e99`. This plan precedes the Module 7
fixture generator and test implementation. Production ownership, lifetime and
format choices are specified in `docs/dictionary-design.md`; C code below is an
external oracle only and never becomes a Rust dependency.

## Metadata ownership and reproducibility

The Python importer owns generated byte strings and JSON value records. A
fixture record contains a relative path, byte length, SHA-256, purpose, and an
optional `expected_output` path into the same collection. Dictionary/frame
associations use names and checked offsets, not addresses. Oracle result
records store method, accepted/rejected outcome, output length/hash, and exact
comparison status. These are plain value records with no unsafe variant.

The C oracle owns bounded temporary input/output buffers and contexts, checks
every reported length and library error, and releases contexts after use. It
may inspect pinned internal entropy helpers to expose exact header boundaries
and dictionary-prepared table metadata. It will be compiled into a temporary
directory against clean pinned sources. Python validates the revision and
source cleanliness, checks every C-produced success against expected bytes,
records source and generator hashes, and supports byte-for-byte regeneration.
No compiler path, timestamp, temporary path or host-specific assertion string
belongs in the reproducible fixture manifest.

`tests/upstream/dictionaries/manifest.json` will use the generic audited shape:
`upstream_revision`, `source_sha256`, generator metadata, and `fixtures` records
with `path`, `size`, `sha256`, and optional `expected_output`. Expected bytes are
stored once and referenced; compact literal expected output may use checked
hex/size/hash metadata. Oracle outcomes and policy expectations are separate
from expected logical-source bytes, since permissive production C accepts some
frames rejected by the selected format policy.

## Dictionary lifetime evidence

Import the seven independent probes originally investigated outside the project
at `/tmp/zstdoxide-dictionary-boundaries`. Every frame has a 1,024-byte window,
unknown content size, no checksum/ID, raw initial output, and a final compressed
block containing one sequence with RLE LL/OF/ML distributions. The raw dictionary
has 2,048 deterministic bytes; its bytes and initial frame bytes use distinct
xorshift32 seeds.

| Case | P | Distance | Match length | Chosen Rust expectation |
| --- | ---: | ---: | ---: | --- |
| Far dictionary reference | 0 | 2,048 | 3 | Accept; dictionary content can exceed output window. |
| Window minus one | 1,023 | 1,087 | 3 | Accept. |
| Window equality | 1,024 | 1,088 | 3 | Accept per format prose; assertion-enabled C disagrees. |
| Window plus one | 1,025 | 1,089 | 3 | Reject per format prose even though production C accepts. |
| Dictionary-to-frame spanning match | 900 | 1,100 | 300 | Accept; copy dictionary suffix then the original first 100 frame bytes. |
| Ordinary output distance equals window | 1,025 | 1,024 | 3 | Accept; this is not a dictionary reference. |
| Before dictionary start | 900 | 2,949 | 3 | Reject invalid distance. |

The source of the policy is `doc/zstd_compression_format.md:1524-1529`.
`lib/decompress/zstd_decompress_block.c:1350-1389` instead asserts at P>=W;
the production copy path around `:930-947` can accept P>W. Record each result
without substituting oracle acceptance for a format rule. Dictionary eligibility
is checked at sequence start; the spanning match may legitimately finish after
W. Its expected bytes must remain distinct enough that a naive ring which
overwrites frame[0] at output byte 1,024 fails at output byte 1,100.

## Reproducible prepared-dictionary witnesses

Run `python3 scripts/generate_upstream_dictionaries.py /path/to/pinned/zstd`
to generate this collection, then repeat with `--check`. Both runs compile the
oracle from clean pinned C sources in temporary directories; an existing static
library is not trusted. The assertions-only boundary build omits compression and
training, while the production oracle includes their pinned sources. The manifest
hashes both generator files and every compiled source plus relevant format/API
definitions. Expected outputs remain ordinary local files covered by the generic
fixture auditor.

`training-samples.bin` contains 256 deterministic 512-byte records. Each record
combines a varying JSON-like request with sparse xorshift32 bytes and its sample
index. `trained.dict` is the exact result of `ZDICT_trainFromBuffer` with a
2,048-byte capacity. `formatted.dict` comes from `ZDICT_finalizeDictionary` with
the complete `boundary-dictionary.raw` content, level 3 statistics, and explicit
ID `0x12345678`. The manifest exposes the independently C-parsed Huffman weights,
FSE normalized counts, section offsets, header length, content length, and repeat
offsets for each generated dictionary. This is oracle data for Rust construction
and interoperability tests; it does not require Rust training to be byte-identical
to the official trainer.

`duplicate-reps.dict` changes the formatted dictionary's three offsets to
`[10, 10, 10]` and its final eight bytes to `x`, retaining the setup of
`tests/fuzzer.c:3265-3309`. `duplicate-reps.zst` compresses 1,024 `x` bytes at
level 19. Because compressor choices alone cannot prove which repeat offset was
used, `duplicate-reps-initial.zst` independently supplies a zero-literal sequence
with offset code zero. Its first match must use dictionary rep2=10; restoring the
ordinary rep2=4 produces different bytes. C decoding verifies the exact three-byte
expected output of that explicit witness.

| Fixture stem | Independently verified contract |
| --- | --- |
| `raw-small-window`, `formatted-id` | The first match uses a 2,048-byte dictionary despite a 256-byte frame window. Raw and formatted loading both restore the exact original source. |
| `formatted-omitted-id` | The frame omits the dictionary ID but still requires selected dictionary content; decoding without it fails. |
| `trained-sample` | C training output is usable; its first block uses treeless literals and all three dictionary FSE tables. |
| `dictionary-treeless-literals`, `dictionary-treeless-four-streams` | Explicit first-block 1X/4X treeless Huffman payloads require prepared dictionary entropy, with 768 literals and zero sequences. |
| `dictionary-repeat-sequences` | The first deterministic trained sample for which C chooses LL/OF/ML repeat mode is retained; independent wire inspection requires all three mode values to equal three. |
| `persistent-concatenation` | Repeating a formatted-dictionary frame decodes both frames with a persistent dictionary. |
| `prefix-first`, `prefix-second` | A reused C compressor uses its raw prefix for the first frame, then drops it; first-frame decoding requires the prefix, while the second succeeds without it. |
| `prefix-once-concatenation` | One prefix plus the first and second frames restores both source copies. |
| `prefix-reused-concatenation` | Repeating the dictionary-dependent first frame succeeds with a persistent dictionary and fails on the second frame with a one-use prefix. |

All fixture names above have `.zst` and `.expected` files. The last case's
`rust_expectation` describes persistent selection; the separate prefix-stream
oracle result records its intended rejection. Each generated frame is independently
checked using direct and prepared decoding and one-byte input with output chunks
1, 7, and 1,024. Prefix cases additionally run one-byte-input prefix streaming.
`first_block` metadata is parsed by Python directly from frame bytes, not inferred
from successful C decode. Compression source buffers do not overlap dictionary
storage, because the C compressor can discard an overlapping history region.

Levels in the manifest reproduce C fixture construction only. Passing these
decoder fixtures does not claim equivalent Rust level selection, dictionary
training algorithms, automatic dictionary maps, static workspaces, or workers.

## Decoder/parser mapping checkpoint

The prepared-decoder checkpoint passes 40 integration tests in
`tests/upstream_dictionary.rs` and 11 parser tests in `src/dictionary.rs`.
The machine inventory maps those declarations to the source groups above.
The exact fixed dictionary's 115-byte header, dictionary/frame IDs, malformed
header-only input, prefix one-use behavior and dictionary-independent second
frame have complete named assertions. Other source groups remain partial where
the original input campaign or an API-specific branch has not been reproduced.

In particular, `fuzzer.c:3124,3146` and
`zstreamtest.c:1198,1240,1269,1320` include C reset/init operations which clear
dictionaries. Rust's selected contract retains dictionaries on either reset;
clearing is explicit through `set_dictionary(None)`. These mappings describe
the adaptation and remain partial. `zstreamtest.c:1551,1831,1884` retain pending
exhaustive sequence-value and compressor table-validity schedules even though
first-block Huffman/FSE defaults and per-frame repeat offsets are now exercised.

`tests/invalidDictionaries.c` now rejects its exact invalid-repeat fixture during
shared Auto/Formatted preparation. Both encoding and decoding require that same
validated `Dictionary`, so the original two constructor failures share one Rust
validation boundary. The malformed fixture is never merely rejected as a frame.
The exact official omitted-ID/prefix-first negative controls now assert failure
without selected content, while the independent prefix-second frame succeeds.

The encoder mapping includes 24 regular tests plus independently executed
CLI checks for 96 streaming and 20 one-shot frames. Useful raw/formatted matches,
all dictionary-ID widths and omission, content-size/checksum/window options,
prefix replacement/lifetime, resets and error recovery run through the public
Rust encoder. Original level/strategy/CDict parameter setup and exact C encoded
byte comparisons remain partial rather than being inferred from interoperability.
Three additional independent regressions require useful retained-output matches
across automatic block boundaries, a flushed two-byte prefix, and a dictionary
match spanning retained frame output into the current block. These strengthen
the existing partial streaming mapping without claiming additional C case parity.

`tests/upstream_training.rs` exercises four regular raw-training contracts and
16 held-out bidirectional official-C roundtrips. Independent C compression totals
decreased from 2,263 to 609 bytes with the Rust-selected content. Training maps as
partial for COVER/fastCover optimization and strategy-specific controls.
The raw-only API intentionally emits content; the separate formatted trainer
constructs its entropy metadata algorithmically as described below.

The formatted-training checkpoint adds seven regular tests in
`tests/upstream_formatted_training.rs`. The exact `fuzzer.c:2665` cyclic case
uses 1 MiB of index-modulo-256 bytes, 128 samples of 8 KiB and a 16 KiB output cap;
it successfully constructs a bounded dictionary with a nonzero ID and a usable
entropy header. This completes the named construction-success assertion without
requiring the Rust training algorithm to reproduce C output bytes. The generic
`fuzzer.c:2675` assertion also runs on exact C-generated CNBuffer data: five
5 MiB seed/profile sources, each trained from its first 1 MiB as 128 samples of
8 KiB with a 16 KiB cap. Independent C verifies IDs/header sizes and decodes every
source byte; the five campaigns cover 26,214,400 bytes in safe and all-feature
release. The original level-4 compression setup remains partial. COVER/fastCover,
shrink, worker and randomized strategy groups remain blocked.

Generated ID and header assertions now exercise both newly built dictionaries
and the original fixed dictionary. The ID/header groups are tracked separately
from preceding strategy-specific builders, which they do not complete. Public
finalization checks cover short-content padding, suffix preservation under the
complete serialized-size cap, explicit/automatic IDs, sample-prefix budgets,
malformed parameters, owned lifetimes and held-out usefulness. Independent C
accepts eight generated dictionaries across 36 source/dictionary pairs in both
directions; its 16 held-out compression outputs total 715 bytes versus 2,288
without the dictionary.

Checked normalized-count serialization now matches pinned C headers at every
supported table log, including zero runs and low-probability counts. Independent
C readers additionally accept 437 generated FSE weight streams and 68 complete
Huffman headers. Those foundations do not yet replay `fse_read_ncount.c`'s
original randomized writer driver or its 79-input external corpus.

The dictionary loader/raw roundtrip adapter preserves the original tail selectors
and selected source bytes. Loader mode/prefix/loading-method consumption and raw
success are exercised; immutable owned handles replace C by-reference lifetimes.
The raw target preserves source/dictionary splitting, prefix choice, checksum
disabling and a smaller compression-bound destination. Unsupported random C
parameters and external sequence producers remain explicit omissions. The entire
2,271-input loader corpus passed safe and all-feature release: 1,919 exact
roundtrips and 352 expected formatted parse rejections. The raw-target corpus
also passed both builds with 13,876 exact roundtrips. Neither replay skips files.
The three training-dependent targets now have adapters and full safe/all-feature
release replays. Their original sample selection is C-verified. Rust training
replaces fastCover, and unsupported advanced-parameter consumption shifts later
scheduling selectors where documented; these target mappings remain partial.

External corpus pinning and replay are separate checkpoints. A completed download
or manifest hash does not change a target's replay status. The structural source
audit likewise verifies links, source bytes and classification; it does not run
the referenced Rust tests.

The dictionary streaming archive shares its complete bytes with the separately
named ordinary streaming archive. Separate target records preserve the different
input interpretation and prevent the ordinary target's replay from satisfying
the dictionary target automatically.

Archive bytes own no codec data structures. Imported metadata comprises immutable
value records; member paths are validated relative paths. The expanded fifteen-
archive snapshot needs 2,682,880,516 unpacked bytes, so the importer raises only
its aggregate limit to 4 GiB. Every archive retains a 1 GiB ceiling and its exact
pinned unpacked-byte bound. Filesystem writes occur in temporary directories;
complete hashes, ZIP CRCs, counts, sizes, path checks and existing-cache byte
comparisons must all pass before an extracted directory is published. Partial
network downloads and range chunks stay outside the project.
